# ADR 0002: PostgreSQL and Prisma ownership

- Status: accepted
- Date: 2026-08-20
- Phase: 0 — foundation and contracts

## Context

BUILD_SPEC.md section 3.1 requires Prisma to be the _sole_ database
migration owner; Python/SQLAlchemy may read but never migrate. Phase 0 only
needs enough of the data model to prove the bootstrap → migrate → seed
pipeline end to end and to back Clerk's minimum-profile mirror (section
3.1, "Auth"); the full schema in section 4 (League, Draft, Player, ...) is
explicitly Phase 1+ work per the phased checklist (section 24).

## Decision

- **Local Postgres**: `postgres:17.7-alpine` via Docker Compose, exposed on
  host port **55432**, not 5432. The dev machine already runs a native
  Postgres 18 on 5432 (and a Homebrew instance on 5433) — defaulting to
  55432 avoids silently colliding with unrelated services. Overridable via
  `POSTGRES_HOST_PORT`. Inside the Compose network, the analytics service
  still reaches Postgres at the standard `postgres:5432`.
- **Prisma version**: `prisma`/`@prisma/client` **7.9.1** (the `latest`
  npm dist-tag), not the `next` dist-tag (`8.0.0-rc.7` at time of writing).
  Prisma 8 is a from-scratch rewrite (`prisma.config.ts`'s `orm` nesting,
  `@prisma/orm-postgres`, a "contract" file replacing `schema.prisma`
  entirely) that is still a release candidate — not stable enough to build
  Phase 1+ on top of.
- **Even on the 7.x stable line, Prisma has already moved past the
  classic `schema.prisma`-only workflow**: `prisma init` (7.9.1) generates
  a `prisma.config.ts` that owns the datasource URL and migration path, and
  the default generator is now `provider = "prisma-client"` (not
  `prisma-client-js`), which emits **plain TypeScript source** into a
  custom `output` directory rather than a compiled client into
  `node_modules/.prisma`. `packages/db/prisma.config.ts` loads the shared
  root `.env.local` explicitly (via `dotenv`) so there is one source of
  truth for `DATABASE_URL` across Prisma CLI, the app, and tests.
- **Driver adapters are required, not optional, on this generator**:
  instantiating `new PrismaClient()` with no arguments throws
  `PrismaClientInitializationError` — Prisma 7's stable client generator no
  longer bundles a query-engine binary by default. `@prisma/adapter-pg`
  (`7.9.1`, pinned to match) + `pg` wrap the Postgres driver;
  `packages/db/src/adapter.ts` is the single place that constructs it from
  `DATABASE_URL`, used by both the shared `prisma` singleton
  (`packages/db/src/index.ts`) and the seed script.
- **Phase 0 schema**: one model, `User` (id as UUIDv7 via `uuid(7)` —
  confirmed supported by validating against 7.9.1 before relying on it —
  `clerkUserId` unique, `role` enum, `plan`/`locale`/`timezone`,
  timestamps). This is exactly what Clerk webhook mirroring
  (BUILD_SPEC.md section 3.1) needs and nothing more; League/Draft/Player/
  etc. are built with their owning Phase 1–2 vertical slices.
- **Seed**: `prisma/seed.ts` upserts one deterministic demo admin user
  (`user_demo_phase0_admin`), wired through `prisma.config.ts`'s
  `migrations.seed` so `prisma migrate dev` and `prisma db seed` both run
  it. Labeled clearly as Phase 0 demo data, not production seed data.

## Consequences

- `packages/db/generated/` (the Prisma client output) is gitignored and
  regenerated by `prisma generate` — added to the bootstrap script.
- Any future Phase 1 model addition is a normal `prisma migrate dev`,
  keeping Prisma as the sole migration owner as required.
- If Prisma 8 stabilizes before Phase 1's full data model lands, revisit
  this ADR rather than upgrading silently mid-phase.
